# 보안과 치트 대비

SKALA 작전에는 게임 서버가 없다. 정적 사이트(GitHub Pages)와 Supabase(Realtime 메시지 중계, Postgres 함수)만 쓴다.
그래서 "클라이언트가 보낸 값을 누가 다시 확인하는가"가 설계의 중심이다. 확인하는 곳은 세 군데다.

| 확인하는 곳 | 믿을 수 있는 정도 | 맡는 것 |
|---|---|---|
| **Supabase DB 함수** | 높음. 클라이언트를 고쳐도 우회할 수 없다 | 닉네임, 포인트·구매·전적 저장, 순위표 |
| **방장 브라우저** | 중간. 손님의 조작은 막지만 방장 자신의 조작은 못 막는다 | 경기 판정(체력·킬·점수), 사격 거리·벽 가림, 이동 검사, 강퇴 |
| **각자 브라우저** | 낮음. 사용자가 마음대로 고칠 수 있다 | 화면 표시, 입력, 자기 위치 계산 |

## 1. 계정과 경제 (서버 DB 함수, `supabase/schema.sql`)

- **직접 접근 차단**: `fps_players` 표는 RLS를 켜고 모든 권한을 회수했다. 브라우저는 `SECURITY DEFINER` 함수 6개(`fps_*`)로만 읽고 쓴다. 공개 키(publishable key)만 사이트에 있다.
- **토큰**: 기기마다 256비트 무작위 토큰을 만들고, 서버에는 SHA-256 해시만 저장한다. 자기 토큰으로 자기 행만 고칠 수 있다.
- **포인트 증가 한도(토큰 버킷)**: 포인트는 여전히 브라우저가 계산하지만, 서버가 늘어나는 속도를 제한한다. 1초에 5점씩 최대 5,000점까지 차는 통과 하루 50,000점을 넘는 만큼은 버린다. 정상 경기(한 판 최대 약 900점)는 걸리지 않는다.
- **구매 검증**: 새로 생긴 무기·이모트·캐릭터는 서버 가격표(`fps_item_price`)로 값을 매긴다. 돈이 모자라면 물건을 받지 않는다. 모르는 id는 버리고, 가진 물건은 저장으로 줄지 않는다. 가격표는 `js/weapons/defs.js`·`js/core/consts.js` EMOTES·`js/core/avatar-defs.js`와 같아야 하고 `tests/account.test.mjs`가 대조한다.
- **새 물건과 배포 순서**: 옛 `fps_save_profile`은 가격표에 없는 물건을 버리면서 줄어든 포인트는 받아들인다. 그래서 클라이언트는 `fps_features`가 `avatars:true`라고 답할 때만 캐릭터 구매를 연다(404·오류·값 없음은 닫힘). 서버 SQL보다 클라이언트를 먼저 배포해도 포인트를 잃지 않고, `schema.sql`을 다시 실행하면 구매가 열린다.
- **장착 캐릭터**: 저장할 때 `loadout.avatar`가 가격표에 있는 `av_` 캐릭터이고 기본이거나 가진 것인지 확인한다. 아니면 기본 캐릭터로 저장한다. 다른 사람에게 보이는 캐릭터는 방 presence(`av`)에 각자 실어 보내는 값이라 고친 클라이언트는 사지 않은 캐릭터로 보일 수 있다. 모양만 바뀌고 몸 크기·히트박스는 모든 캐릭터가 같아 판정에는 영향이 없다. 받는 쪽은 모르는 값을 기본 캐릭터로 그린다.
- **전적 한도**: 킬은 1초에 1번(최대 300), 승리는 30초에 1번(최대 10)씩 차는 통으로 제한한다. 순위표가 킬·승리 순이라 순위 조작을 막는다.
- **서버 값 우선**: 저장 결과로 서버가 받아들인 포인트·무기·전적을 돌려주고, 클라이언트는 그 값을 따른다(`js/account/index.js` `adoptSaved`).
- **가입 속도 제한**: 닉네임 등록은 같은 IP에서 한 시간에 60번까지다. IP 원문은 저장하지 않고 해시만 센다(`fps_rate`). 교실처럼 여러 명이 한 IP를 써도 넉넉한 값이다.

## 2. 경기 (방장 브라우저, `js/game/anticheat.js`, `js/game/session.js`)

- **판정 권한**: 체력·킬·점수·라운드는 방장의 `match.js`가 정한다. 손님이 자기 화면의 체력을 고쳐도 방장 판정으로 죽는다.
- **사격 거리 재계산**: 쏜 사람이 적어 보낸 거리를 믿지 않는다. 방장이 위치 기록(`sync.getRemoteAtHost`, 방장 자신은 `selfTrail`)으로 쏜 사람과 맞은 사람의 자리를 다시 재고, 더 가깝다고 우기면 방장이 잰 거리(여유 3 m, 칼 1.5 m)로 피해와 사거리를 계산한다.
- **벽 가림**: 맵 충돌 정보로 시야를 확인한다. 지연을 감안해 맞은 사람의 지난 0~450 ms 자리 중 하나라도 보였으면 인정하고, 모두 벽에 막혔으면 버린다.
- **이동 검사**: 위치가 물리적으로 가능한지 본다. 최고 속도(버니합 상한·발판 포함)의 1.35배를 넘거나, 포털 출구·스폰이 아닌 곳으로 8 m 넘게 순간이동하거나, 점프보다 빨리 솟으면 위반이다.
- **위반 누적과 강퇴**: 지연으로도 생길 수 있는 위반(벽 가림·과속)은 1점, 정상 클라이언트에서는 나오지 않는 위반(연사 한도 초과·순간이동)은 2점이다. 20초에 6점이 쌓이면 경기에서 빼고 강퇴 메시지를 보낸다. 고친 클라이언트는 강퇴를 무시할 수 있으므로, 그 뒤로도 그 사람의 사격·수류탄·장비·채팅을 버린다.
- **팀전 아군**: 아군 사격은 꺼져 있고, 총알은 아군 몸을 통과해 뒤의 적에게 맞는다.

## 3. 방과 통신

- **비밀번호 방**: 비밀번호와 방 id로 PBKDF2(SHA-256, 10만 번)를 돌린 값을 채널 이름에 붙인다(`js/net/secret.js`). 비밀번호는 어디에도 보내지 않고, 모르면 같은 채널을 찾을 수 없다. 서버가 검사하는 잠금이 아니라 채널 이름을 숨기는 잠금이라, 짧은 비밀번호는 시간을 들이면 맞힐 수 있다(친구끼리 쓰는 수준).
- **메시지 크기·속도**: 무료 플랜 한도에 맞춘 전송 예산과 레이트 리미터(`js/net/limits.js`). 받은 메시지는 모두 형식 검사(`js/game/protocol.js` decode)를 거친다.

## 4. 웹 (각자 브라우저, `index.html`)

- **CSP**: 스크립트는 이 사이트와 jsDelivr, importmap(해시로 허용)만 실행한다. 접속은 이 사이트와 설정된 Supabase 프로젝트만 허용한다. `object-src 'none'`, `base-uri 'self'`.
- **CDN 무결성(SRI)**: three.js·cannon-es는 importmap의 `integrity`(sha384)로 내용까지 확인한다. CDN이 변조돼도 실행되지 않는다.
- **XSS**: 화면은 모두 `textContent`로 그린다(`innerHTML`·`eval` 0곳). 닉네임·방 이름·채팅은 길이를 자르고 정리한다.
- **팀 채팅**: 보내는 쪽이 팀원을 받는 사람으로 정해 보낸다. 중계 서버는 받는 사람에게만 전달하고, 받는 쪽은 같은 팀이 보낸 팀 채팅만 보여 준다(MODES.md 8절). Supabase 전송에서는 프레임이 모두에게 가므로 고친 클라이언트는 볼 수 있다.
- **움직이는 지형**: 방장의 벽 가림 검사는 움직이는 지형을 빼고 본다. 쏜 순간과 확인하는 순간 사이에 자리가 바뀌어 정상 사격이 위반으로 잡히지 않게 한 것이다. 고정 벽 뒤 사격은 그대로 거절한다.
- **문**: 가까이 오면 열리는 문도 움직이는 지형이라 방장의 벽 가림 검사에서 빠진다. 문은 화면마다 자기가 보는 사람 위치로 여닫으므로(원격 위치는 약 0.1초 늦다) 쏜 사람 화면에서는 열려 있고 방장 화면에서는 아직 닫혀 있을 수 있기 때문이다.
- `tests/web-security.test.mjs`가 CSP 해시와 importmap, 무결성 해시, 인라인 스크립트 0개를 확인한다. QA 서버는 가짜 Supabase(127.0.0.1)를 쓸 때만 로컬 주소를 더한다.

## 5. 남은 한계 (지금 구조로는 막을 수 없는 것)

1. **방장 자신의 조작**: 방장 브라우저가 판정하므로 방장이 고친 클라이언트를 쓰면 무엇이든 된다.
2. **사칭**: Realtime 메시지의 보낸 사람 id는 클라이언트가 정한다. 남의 id로 보내는 것을 서버가 막지 않는다. 강퇴당한 사람이 새 탭으로 다시 들어오는 것도 막지 못한다.
   중계 서버(`server/relay`, `transport: 'relay'`)를 쓰면 프레임의 보낸이가 그 연결이 참가할 때 쓴 presence 키와 같아야 하므로 이미 참가한 사람 이름으로 보내지는 못하고, `sendTo`·강퇴 메시지는 대상에게만 간다. 다만 참가할 때 남의 id를 쓰는 것과 강퇴 뒤 재참가는 아직 막지 못한다(신원 토큰이 다음 단계).
3. **정보 치트**: 모든 플레이어의 위치가 모두에게 가므로 벽 투시는 막지 못한다. 에임봇은 위치·시야 검사를 통과하므로 통계로 탐지해야 한다.
4. **경기 중 무기 소유**: 방장은 손님이 그 무기를 샀는지 모른다. 사지 않은 무기를 경기에서 쓰는 것은 막지 못한다(서버에 저장되지는 않는다).
5. **한도 안의 농사**: 포인트·전적은 한도 안에서는 여전히 브라우저 계산을 믿는다. 고친 클라이언트는 한도만큼은 매일 얻을 수 있다.

## 6. 다음 단계: 권위 서버

위 한계 1~4는 **권위 서버**(authoritative server)로만 해결된다. 클라이언트는 입력만 보내고 서버가 이동과 사격을 시뮬레이션한다.
클라이언트 예측과 서버 보정, 쏜 사람 시점으로 되감는 지연 보정을 쓴다. 이 저장소의 물리·이동·경기 규칙(`js/engine/physics.js`, `js/engine/movement.js`, `js/game/match.js`)은
three.js 없이 node에서 도는 순수 모듈이라 서버로 옮기기 좋다. 상시 돌아가는 서버(작은 VM이나 Cloudflare Durable Objects 등)가 필요하다.
경기 결과도 서버가 계산하면 포인트·전적 한도(위 5번)도 정확한 값으로 바꿀 수 있다.
